The Learning Board is a five-phase lesson surface — Read → Cover → Recite → Test → Results — that renders any unit from a single data file. It lives at /board/[unitKey], separate from the older lesson flow so the two can run side by side.

How it is built

Architecture in one page

The whole design rests on one boundary: units are data, the player is code. Adding a unit means writing one data file and adding one line to a registry. It should never mean touching a component.

FileRole
lib/boardUnits/types.tsThe contract. Every shape a unit can express. Read this first — it is documented and it is the spec.
components/board/DrawingBoard.tsxThe player. Renders all five phases and every stage. Subject-agnostic; never edited per unit.
lib/boardUnits/<unit>.tsOne file per unit. All content lives here.
lib/boardUnits/index.tsRegistry — BOARD_UNITS, keyed by unitKey. One line per unit.
public/board-art/Cropped artwork panels, referenced by path from unit files.
app/board/[unitId]/page.tsxRoute. Resolves from BOARD_UNITS; pulls existing question papers from the DB if a row exists.

Stages

A unit declares a default stage, but any individual frame overrides it by carrying its own shape — a frame with diagram draws a diagram whatever the unit says. That is what lets one unit mix a number line with a photograph.

Available: grid · numberLine · text · diagram · bar · chart · timeline · image.

Two rules inside the player worth knowing

  • Grid units in, pixels out. Unit files use grid coordinates (0–10) only. The player owns the mapping to SVG space. Breaking this is what previously put shapes off their own grid.
  • First answer is final. Grading locks on the first press; later presses change the explanation only. This was an explicit product decision — a wrong answer scores zero even though it is still explained.

Adding a unit

1. lib/boardUnits/cambridge-5-english-4.ts   # the content
2. lib/boardUnits/index.ts                  # import + one registry line
3. npx tsc --noEmit && npm run build        # both must be clean
4. git push                                 # Railway deploys from main

The board is then reachable at /board/<unitKey> immediately. It will not appear in the student unit list until a matching Unit row exists in the production database — see Open decisions.

Learned the hard way

Rules that will bite you

These are not style preferences. Each one came from something that shipped wrong and had to be pulled back.

Verify any figure that asserts a number

NotebookLM is fine for any subject. The dividing line is not English versus maths — it is whether the picture asserts a value. Image models cannot reliably hold an exact count, coordinate or angle, and the generated figures were confidently wrong in ways a child would catch by counting:

  • dot labelled (4,3) — plotted at (7,6)
  • corner labelled (2,6) — plotted at (2,7)
  • triangle captioned “1 up” — moved about 3 up
  • “a 10-part chocolate bar” — drawn with 7 pieces
  • “14 tenths” — drawn as 8 rods

The test to apply: could a child count, measure or read a value off this picture and get a different answer from its own caption? If yes, it must be hand-authored and checked numerically — Maths Unit 2 does this, with a computed 60° ray and an equilateral apex at 190 − √(140² − 70²) so all three sides are exactly 140 (drawn by eye it was 0.04 out). If no — a fable scene, a mood contrast, a labelled diagram of a process — generate it freely. That applies to science, geography and history figures just as much as maths ones.

Textbook page offsets drift — always read the printed folio

Both textbooks are scans with no extractable text, and the scan index does not map to the printed page by any constant. Some sheets are two-page spreads, so the offset shifts mid-book.

  • English: index +3 up to about page 21, then +5 from page 26 on.
  • Maths: +2 through the early units, but +0 by page 151.

Method that works: render each page, crop the bottom 8% of the image, and read the printed folio directly. A naive constant offset would have put every Unit 2 reference two pages out — which defeats the entire purpose of page references, since a child is meant to open the book and check.

Set texts are in copyright — reference, never reprint

English Unit 3 is taught from Valerie Bloom’s Sandwich (p42) and Alan Smith’s Emily Hurricane (p53). The board points the child at the page and works from the book’s own glossary, rhyme pairs and syllable table, quoting only short fragments with attribution.

For the Test, an original poem (The Last Bus) was written for the board. That serves the pedagogy too — the Test is supposed to be unseen material.

Verify on the live page, not in the code

The image stage had four separate defects stacked on top of each other, each only visible once the one above it was fixed:

  1. Hotspots positioned against the container, not the picture — every label pointed at empty background.
  2. The measurement was wiped by an effect that ran after it.
  3. The stage was starved of height by a four-row concept stepper.
  4. The measurement was never taken at all on first paint.

#4 is the subtle one and will recur elsewhere: the <img> is in the server HTML, so the browser usually finishes loading it before React hydrates — onLoad never fires. Measure from a ref (checking img.complete) and keep onLoad only for images that genuinely arrive later. Reading the code would not have found any of these.

A session is not a person being active

Sessions last 30 days. Treating “has an unexpired session” as “logged in” would badge someone who signed in three weeks ago and closed the tab as active. Live data proved it: 3 accounts had live sessions, only 1 was actually present.

Presence is therefore derived from Session.lastSeenAt, stamped by getCurrentUser at most once every 5 minutes. Signed-in and active are shown as the two separate facts they are.

Runbook

How to do the recurring things

Deploy

Railway deploys from main on push. The start command is npx prisma migrate deploy && npm run start, so migrations apply themselves — commit the migration folder and it runs before the app starts. Budget roughly 4–5 minutes.

Verifying a deploy — and what does not work

The board pages require auth, so curl returns a ~6KB login shell, not the page. Two verification methods that were tried and are useless: checking for HTTP 307 (the old build returns it too) and diffing buildId (App Router never emits it). What works:

  • New artwork: poll the asset path for a 200.
  • Code changes: open the page in the browser and inspect the DOM.

Mapping a new chapter to real textbook pages

1. Render a contact sheet of candidate pages     (PyMuPDF, ~60 dpi)
2. Crop the bottom ~8% of each page              # the printed folio
3. Read the folios to fix the offset for THAT range
4. Render the 3–5 teaching pages at ~115 dpi and read them
5. Write concepts with pages[] + storyReference + the book's own examples

Generating artwork — NotebookLM (any subject)

All 13 artwork panels came from Google NotebookLM’s Infographic generator, in a notebook whose sources include the two textbook PDFs. It is used for pictures only — never for text, answers or teaching content, which all come from the book itself.

Use it for any subject. So far it has only been used on English units, but nothing about the tool is English-specific: a science apparatus scene, a geography map, a history timeline illustration are all good candidates. The one constraint is the rule above — if the figure asserts a countable or measurable value, generate it only if you are willing to verify every number on it, and hand-author it otherwise.

The click path: Studio panel → Infographic → the Customise dialog → scroll down to “Describe the infographic that you want to create” → paste the prompt → Generate now. It takes 1–4 minutes and appears at the top of the Studio list; download via the row’s ⋮ → Download.

  1. One wide poster, four clearly separated panels, each with its own bold title — one generation covers 3–4 concepts, so the whole cycle is ~10 minutes per poster.
  2. State that spelling is critical and list the risky words. Without that line, posters came back with Statament, shaw, menasing. With it, clean. This is the single highest-value sentence in the prompt.
  3. The download lands as a hidden ~/Downloads/.com.google.Chrome.XXXXXX file (a named .png may also appear). Sort by time to find it.
  4. Crop per panel, trim the watermark at the bottom-right, target ~150–250KB.
  5. Keep panels landscape or square. Portrait panels cannot be both large and fully visible on a wide, short stage — split a tall panel into its two teaching moments instead.
  6. Proofread every panel at full size before wiring it. Several defects were caught only this way.

Worth knowing: because the textbooks are sources, it sometimes pulls real content — the biography poster independently chose Poorna Malavath and quoted the book’s own sentence. Pleasant, but it still has to be checked; the same model produced every one of the wrong maths figures.

Testing with the Claude Chrome plugin

Board pages require auth, so curl cannot see them. Every live verification this session was done through the Chrome plugin against the real deployed site.

  • tabs_context_mcp first, every session, to get valid tab IDs — never reuse IDs from a previous session.
  • browser_batch to combine navigate → wait → screenshot in one round trip. Doing these as separate calls is markedly slower and costs more; batch whenever the next 2+ steps are predictable.
  • javascript_tool to measure the DOM.
  • Screenshot last, to confirm what a child would actually see.

Measure the DOM — do not infer from a screenshot

I twice read a screenshot wrongly, mistaking a wide container border for the edge of the picture, and reported a bug fixed when it was not. One javascript_tool call settled it in seconds: boxInline: null, aspectRatio: "auto" proved the sizing had never applied, and after the fix 307×448 with min-height 448px proved it had.

Screenshots answer “does this look right”. Only the DOM answers “is this actually doing what I wrote”. Use both, in that order, and trust the second.
